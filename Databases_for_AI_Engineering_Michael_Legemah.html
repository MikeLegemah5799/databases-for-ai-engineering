Pick the store by the question you ask

An AI system asks four different kinds of questions: what is similar, what is connected, what is true right now, and what happened. Each one has a database built for it.

Start with Postgres, graduate on evidence

One database with pgvector, JSONB and full-text search covers most products until a measured limit says otherwise. Add a specialist store when a number forces it, not when a diagram looks cleaner.

The vector index is a cache, not the record

Embeddings are derived data. Keep the source text and the embedding model version in a system of record so you can rebuild the index when the model changes.

Filter in the database, not after the LLM

Tenant, ACL and freshness filters belong in the retrieval query. Post-filtering top-k results quietly drops recall and risks leaking documents the user should never see.

1 · Vector databasesPinecone · Weaviate · pgvector

Find what means the same thing, not what says the same words

OpenClose

A vector database stores embeddings and answers one question fast: which stored items are closest to this query vector? That's the retrieval step behind RAG, semantic memory, deduplication and recommendations.

Problem it solves

Keyword search misses paraphrases and synonyms, and brute-force comparison against millions of vectors is too slow to serve.

What you get

Approximate nearest-neighbour search in tens of milliseconds, combined with metadata filters and, in the better engines, keyword scoring.

Core paradigm how embeddings are indexed and queried

An embedding model maps text, images or audio to a vector of 384 to 3,072 floats, so that similar meaning lands close together. Exact search compares the query against every vector. That doesn't scale, so engines build an approximate nearest-neighbour (ANN) index and trade a little recall for a lot of speed.

  • HNSW is a layered proximity graph. Best recall and latency, but it lives in RAM and costs more to build. Knobs: M (links per node), ef_construction (build effort), ef_search (query effort).
  • IVF / IVFFlat clusters vectors and probes the nearest clusters. Cheaper to build, needs training data, recall depends on nprobe.
  • DiskANN-style indexes keep the graph on SSD with a compressed copy in memory, which makes very large corpora affordable.
  • Quantization (scalar, product, binary) shrinks vectors 4 to 32x. Pair it with a rescore against full-precision vectors to recover recall.
  • Distance metric must match the embedding model: cosine for most text models, inner product for normalised vectors, L2 for some vision models.

Hybrid search blends dense (semantic) and sparse (BM25 keyword) scores, usually by reciprocal rank fusion. It matters because embeddings are weak at exact tokens such as part numbers, error codes and names. Add a cross-encoder reranker on the top 50 to 100 candidates and quality jumps again.

Pinecone: Serverless vs. Pod-based index types

Serverless separates storage from compute. You pay for storage plus read and write units, capacity scales automatically, and idle indexes cost little. It's the default for new workloads, spiky traffic and multi-tenant apps (one namespace per tenant). Pod-based is the older provisioned model: you choose pod type and size (storage-optimised s1, performance-optimised p1 / p2) and add replicas for throughput. It gives predictable latency and cost under steady, heavy load, but you size and resize it yourself. Treat Pod-based as legacy unless you have a specific capacity reason, and confirm current plan limits in Pinecone's docs before committing.

pgvector in practice the pattern worth memorising

-- one table, relational columns and the embedding together
CREATE EXTENSION vector;
CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  tenant_id   uuid   NOT NULL,
  doc_id      uuid   NOT NULL,
  body        text,
  embed_model text   NOT NULL,   -- rebuild trigger when this changes
  embedding   vector(1536)
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

SET hnsw.ef_search = 80;               -- recall vs. latency, per session
SELECT id, body, embedding <=> $1 AS dist
FROM chunks WHERE tenant_id = $2
ORDER BY embedding <=> $1 LIMIT 20;

The pitfall is filtered search: an approximate index scans the nearest neighbours first and then applies WHERE, so a selective filter can return fewer rows than asked. Recent pgvector versions add iterative index scans to fix this; for hard multi-tenancy also consider partitioning by tenant. Indexes cap at 2,000 dimensions for vector and 4,000 for halfvec, so use a shorter embedding or halfvec for the larger models.

When & why to use which the checklist

Choose a pure-play vector DB (Pinecone, Weaviate) when:

  • You expect tens of millions of vectors or more, or growth you can't predict.
  • Retrieval has a hard p99 latency SLA and heavy query concurrency that shouldn't share a box with your OLTP traffic.
  • You want no infrastructure work (Pinecone) or native hybrid search and multi-modal out of the box (Weaviate).
  • Vector search is the product, and a dedicated team owns relevance tuning.

Choose pgvector (or Aurora / Neon with pgvector) when:

  • Your corpus is under roughly 10 to 50 million vectors and fits in memory beside your data.
  • You need joins, transactions and row-level security in the same query as similarity (permission-aware RAG).
  • Operational simplicity wins: one backup, one failover, one access-control model, one bill.
  • You're prototyping. You can always move the vectors out later; you can't easily un-split a system.

2 · Graph databasesNeo4j · Amazon Neptune

When the answer lives in the connections, not the documents

OpenClose

Vector search returns passages that sound relevant. A graph returns the explicit entities and relationships those passages describe, so an LLM can reason across several hops with facts it can cite.

Problem it solves

Questions like "which suppliers share a risky subcomponent?" need joins across many relationships. Top-k chunks rarely contain the whole chain.

What you get

Traversal that costs the same on a billion nodes as on a thousand, plus structured provenance for every claim the model makes.

Core paradigm Property Graph vs. RDF

A Property Graph has nodes (entities, with labels), edges (typed, directed relationships) and key-value properties on both: (:Person {name})-[:WORKS_AT {since}]->(:Company). It's flexible and developer-friendly, queried with Cypher, openCypher or Gremlin.

RDF models everything as subject-predicate-object triples with global URIs, queried with SPARQL. It's built for ontologies, formal reasoning and merging datasets from different sources. Choose it when interoperability and standards matter; choose Property Graph when the team is building an application.

Graphs are "index-free adjacency" stores in the native engines: each node holds direct pointers to its neighbours, so a hop doesn't scan a table. In a relational database the same traversal is a chain of joins whose cost grows with every hop.

Why graphs matter for AI knowledge graphs and GraphRAG

Plain vector RAG has four recurring failure modes. GraphRAG addresses each by giving the LLM structure along with text:

  • Multi-hop questions. The answer spans documents that never mention each other. A graph walks the path explicitly: Drug → targets → Pathway → linked adverse events.
  • Global questions. "What are the main themes across this corpus?" has no matching chunk. Community detection (Leiden) over the entity graph, with LLM-written community summaries, answers it.
  • Ambiguous entities. "Apple" the company and the fruit embed close together. Resolved nodes with typed edges disambiguate.
  • Explainability. Each answer can cite the exact nodes, edges and source chunks it used. That matters for regulated domains, and it makes hallucinations easier to audit.

The cost is real: building the graph means running an LLM extraction pass over the corpus, resolving duplicate entities, and maintaining an ontology. Do it when relationship questions are a core use case, not as a default.

The retrieval pattern vector seeds, graph expands

// 1. vector search finds seed chunks/entities; 2. expand 2 hops around them
CALL db.index.vector.queryNodes('chunk_embedding', 8, $queryVec)
YIELD node AS chunk, score
MATCH (chunk)-[:MENTIONS]->(e:Entity)
MATCH path = (e)-[*1..2]-(related:Entity)
WHERE ALL(r IN relationships(path) WHERE r.confidence > 0.7)
RETURN chunk.text, e.name, [r IN relationships(path) | type(r)] AS rels,
       related.name, score
ORDER BY score DESC LIMIT 40;

Cap the hop depth and filter on edge properties. An unbounded variable-length match through a "super-node" (an entity connected to millions of others) is the classic way to take a graph database down.

3 · Relational databasesPostgreSQL · Neon · SQLite · Amazon Aurora

The deterministic backbone under a probabilistic system

OpenClose

LLMs are non-deterministic, so everything around them should be boring and exact. Users, permissions, billing, audit trails and workflow state belong in a database that enforces constraints and never loses a write.

Problem it solves

Agents that retry, branch and run in parallel corrupt state unless every update is atomic, isolated and auditable.

What you get

ACID transactions, foreign keys, mature tooling, and with extensions it also does vector, full-text and JSON in one place.

Core paradigm schema, ACID, SQL

Data lives in typed tables with enforced constraints (primary and foreign keys, CHECK, uniqueness). Transactions are atomic, consistent, isolated and durable, so a multi-step update either fully happens or doesn't. SQL gives you joins, window functions, CTEs and a planner that optimises ad hoc questions you haven't thought of yet. That flexibility at read time is the thing key-value stores give up.

Modern Postgres also absorbs neighbouring paradigms: JSONB for semi-structured data, tsvector for full-text search, pgvector for similarity, row-level security for tenant isolation, and logical replication for change data capture into other stores.

Neon's branching is the standout for agent work. A branch is a copy-on-write fork of the full database in seconds, so an agent can try a risky migration, a bulk update or a generated schema in isolation, and you throw the branch away if it goes wrong. It's the safest way to give an agent a real database. SQLite in WAL mode handles many readers and a single writer, which is plenty for a desktop copilot or an edge device.

What belongs here AI use cases

  • Application metadata and user profiles: tenants, roles, preferences, quotas, billing.
  • Authorisation: the permission model that retrieval must respect, enforced with row-level security.
  • Deterministic agent state: workflow step, approvals, idempotency keys, job queues (SELECT … FOR UPDATE SKIP LOCKED), and framework checkpointers.
  • Audit and tool-call ledgers: which model, prompt version, tool and arguments produced which side effect. Append-only, queryable, defensible.
  • Eval results and feedback: runs, scores, judge verdicts and thumbs-up data you'll join against traces.
  • Document registry: doc IDs, versions, hashes and ingestion status that the vector store points back to.

The reason it stays the gold standard: a financial transaction, a permission change or an approval can't be "eventually right". Constraints make illegal states unrepresentable, and no prompt can talk its way around a foreign key.

Store what the model said as it was said, at any volume

OpenClose

Conversations, tool outputs and raw LLM payloads are nested, irregular and append-heavy. Document and key-value stores take them as they arrive, with no migration, and scale out by adding partitions.

Problem it solves

Every new prompt format, tool and model changes the shape of what you log. Rigid schemas turn each change into a migration.

What you get

Schema-flexible writes, horizontal scale, and fast reads by key such as session_id or user_id.

Core paradigm flexible documents and key-value access

A document store keeps JSON-like documents with nested fields and arrays, indexes the fields you choose, and queries inside them. A key-value store is simpler and faster: you give a key, you get an item, and every access pattern has to be designed up front around that key. Both shard automatically across nodes by key, which is why they absorb write volume that would strain a single relational primary.

The tradeoff is the mirror image of relational: you get write scale and schema freedom, and you give up ad hoc joins and cross-document transactions as a first-class feature.

Agent memory pattern short-term and long-term

Short-term (working) memory is the current thread: recent turns, tool results, scratchpad. It's keyed by thread_id, read on every step and expired with a TTL. Long-term memory is what survives across sessions: user facts, preferences, past outcomes. Store the raw episodes in the document store, then extract durable facts and index them for similarity (vector) or relationships (graph).

// DynamoDB single-table design for conversation memory
PK = "THREAD#<thread_id>"     SK = "MSG#<ulid>"      // time-ordered, range-queryable
attrs: role, content, tool_calls, model_id, prompt_ver, tokens, ttl
GSI1: PK = "USER#<user_id>"  SK = "THREAD#<last_active>"   // "my recent chats"

// "load the last 20 turns" = one Query, ScanIndexForward=false, Limit=20

Always log model_id and prompt_version with each message. When quality shifts, that's the field that lets you tell a model change from a data change.

What belongs here AI use cases

  • Conversation history and episodic memory, in full fidelity.
  • Raw LLM input and output: prompts, completions, token counts, latencies and tool traces for replay, evals and fine-tuning data.
  • Unparsed payloads before ingestion: the landing zone for scraped pages, API responses and uploaded files, so the chunking and embedding pipeline can be re-run from the original.
  • Event and feedback streams: DynamoDB Streams or change streams trigger downstream indexing.

Large blobs (full PDFs, audio, images) go in object storage such as S3, with a pointer in the document. Keeping the payload out of the item avoids both size limits and cost.

Production pitfalls that decide the choice

These are the issues that show up after launch. Check them before you commit to a store.

Embedding driftStore embed_model and version per row. Upgrading models means re-embedding the corpus and swapping indexes behind an alias, so keep the raw text. Mixing vectors from two models in one index silently wrecks recall.
Permission leaksEnforce tenant and ACL filters inside the retrieval query (namespaces, RLS, metadata filters). Never rely on the LLM or on post-filtering to hide documents.
Dual-write inconsistencyWriting to Postgres and a vector store separately will drift. Use an outbox table or change data capture so the index is derived from the record, and run a periodic reconciliation job.
Graph blow-upsBound hop depth, filter on edge properties and handle super-nodes explicitly. Version your extraction prompt, because a changed prompt creates a differently shaped graph.
Unbounded memory growthPut TTLs on short-term memory, summarise old turns, and consolidate episodes into facts. Raw logs grow forever; recall quality drops when you retrieve from all of them.
Evaluating retrievalMeasure recall@k and MRR on a labelled set before tuning the LLM. Most bad answers are retrieval failures. Re-run the set whenever you change chunking, embeddings, index parameters or the database.
